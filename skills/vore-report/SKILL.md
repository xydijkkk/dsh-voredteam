# 报告规范（vore-report）

## 一、报告的七项必备结构（缺一不算交付）

1. **信息收集**：每个站点的 Web 服务版本、中间件、开发语言指纹、操作系统、使用的程序/组件；资产按类别归拢（域名/IP/端口/服务/业务系统）。
2. **漏洞验证详情**：必须包含**完整的原始 HTTP 请求包（Request）与服务端响应包（Response）**，并**标注关键差异**（哪个参数/头/编码导致行为翻转）。
3. **漏洞利用（Exploit）**：具体载荷（Payload）+ 执行结果；可复现的最小步骤（1/2/3）。
4. **完整通关攻略（Writeup）**：从零开始的逐步复盘，包含思路推导——为什么先测这个、看到什么信号转向下一步。
5. **URL 规范**：报告中每个信息都使用**完整 URL**（原始数据包除外）。
6. **按资产类别分篇**：Web 测试 / App 逆向发现的资产 / 小程序 / 电脑应用逆向，各自成篇，不要混在一份里。
7. **失败与待人工项单独成篇**：测试失败、需要人工查看、未决候选、超出授权而被拦的动作，单列一篇。

## 二、高危判定（决定"线索"还是"漏洞"）

- **算漏洞**：真正能危害该网站/公司的——RCE、越权拿到他人真实数据、任意文件读写、SQL 注入可拖库、认证绕过、能接管账号/后台。
- **只算线索**：需要苛刻前置条件的，例如 Cookie 缺 HttpOnly/Secure/SameSite、未强制 HTTPS（明文与加密响应逐字相同）、仅信息层面的版本号暴露、需中间人/钓鱼才能完成的利用链。
- **判级依据**：以**实际影响**定级，不以扫描器标题定级；疑似一律标「疑似」，不得为了好看升级。

## 三、证据纪律（与黑板一致）

- 每条结论必须挂可复现证据：完整请求/响应包路径、PoC 脚本路径、命令回显、文件哈希；长数据落文件，报告里写指针。
- **发现 ≠ 真实存在；发现 + 验证 = 真实有效**。未验证的写「疑似」。
- 上报前排除误报三来源：环境差异（本地能打穿目标不行）、工具自身误报、我方测试残留（自己留下的文件/账号/载荷）。
- 命令执行类验证只做只读（`whoami`/`id`/`pwd`）；文件上传成功后**必须写明上传文件的确切路径**。

## 四、每条漏洞的字段模板

```
## <序号>-<漏洞名>
- 名称 / 等级（含判级理由：影响是什么、能造成什么后果）
- 地址（完整 URL，含参数）
- 目标资产与边界（属于哪个资产、是否在授权范围内）
- 前置条件（需要什么凭据/角色/网络位置）
- 测试过程：步骤 + 关键请求响应（原文）+ 关键差异标注
- 证据：evidence/xxx.txt（请求/响应原文）、exp/<id>.py（复现脚本）
- 利用载荷与执行结果
- 影响与危害（落到业务与数据：影响多少用户/什么数据/能否扩大）
- 修复建议（针对这个点、这个位置的具体修法，不写套话）
- 复现脚本：exp/<id>.py（参数化 -u/--target，只读、破坏性步骤默认关闭，exit 0 = 复现成功）
```

## 五、收口前的自检清单

- [ ] 每条漏洞都有原始请求包 + 响应包 + 关键差异标注
- [ ] 每条都有完整 URL 与影响说明
- [ ] 高危项都经过**独立复核员**（`reviewer`）确认，且复核结论（确认/挑战）写进「测试过程」
- [ ] 疑似项与线索项单列，不混入高危结论
- [ ] 失败项/待人工项单独成篇，含"试过什么、为什么失败"
- [ ] 按资产类别分篇（Web / App 逆向 / 小程序 / 桌面）
- [ ] 报告里的证据路径在盘上真实存在（逐条 `Test-Path`）
- [ ] 成果已同步到黑板（每条漏洞一条事实：`category=vuln` + `severity`/`target`/`poc`/`fix`），作战面板「任务汇总」可见
